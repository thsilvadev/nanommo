# Design — Refining Hand Equipment, Mastery Skills, Status Effects

## Current implementation findings

1. Swordsmanship applies Bleed to the foe with `applyStatus(foe, 'bleed', ...)`. The underlying state target is correct, but both Grind and Battle History text formatters use `event.actor` as the affected unit and ignore `event.target`. A DoT event's actor/source identifies who applied the status, not who takes its damage.
2. The catalog's Bleed effect has `damagePerStack: 5`, `intervalTicks: 5`, and `maxStacks: 5`. The simulator currently writes `damagePerTick = 5 * rank`, which matches the now-confirmed rank damage scaling, but it reports generic `damageType: 'status'` and the tooltip/status log do not clearly communicate the pure damage contract. Preserve rank scaling, source the value from catalogue effect fields, and make it explicit pure damage that ignores DEF and MDEF.
3. The character summary currently projects Freeze only. The Grind monster STATUS list reads only the opening monster snapshot, so applications/stack changes/expiry during the battle are missing from its live UI.
4. The existing Freeze icon's framing, icy-blue color, size and placement are liked; replace only the “Fre” lettering with a crisp snowflake. Preserve the existing STATUS slot sizing, positioning and real-time lifecycle.
5. Mastery currently posts an API mutation per icon click and shows rectangular text nodes. The right category list omits Rune. Mastery XP/level/available points are loaded when the Character component initializes but not refreshed on battle resolution.
6. Current player skills named in the catalog include Wisp Flow, War Cry, and Stored Essence. The runtime implements Wisp Flow's damage as `MATK + remaining SP after its cost`; it does not currently add `25 × skill rank`. War Cry uses a fixed +20 DEF for 10 ticks at every rank. Stored Essence reduces skill SP costs and is part of the existing Rune skill data.
7. The monster skill catalogue has Enraged Strike, Regenerate, Ground Slam, and Ice Bolt. Current monster combat snapshots hardcode `sp = 0`, `maxSp = 0`, and zero SP regeneration. The canonical root `monsters.json` Wailing Wraith Gambit lists `silence → attack` first and Ice Bolt second, while `apps/frontend/public/data/monsters.json` lists Ice Bolt first and `silence → attack` second. Preserve the canonical/root behavior and sync only this Wraith Gambit order into the frontend mirror; tests should assert the action/condition semantics and gauge-specific evaluation, not a brittle array index. The evaluator still checks cooldown, range and SP legality before an action can run.
8. Current code decrements monster cooldowns while the cast gauge accrues, allowing Ice Bolt (`baseCastTicks = 2`, `cooldownTicks = 1`) to repeat every two ticks. That does not match the user's confirmed contract. Cooldown begins when an action resolves and blocks the next activation during the following `cooldownTicks` tick(s); an action may not advance a new cast while it is cooling down. For Ice Bolt: initial resolution T2, T3 blocked, next activation/cast starts T4, continues T5, resolves T6; then T7 blocked, T8 next cast starts, T9 casting, T10 resolves. Expected resolved-event cadence is T2/T6/T10..., deterministic and sequential rather than overlapping.
9. Current code accrues the character movement gauge only while `movementIntent` is true; this is a defect against the confirmed behavior. The gauge starts at zero at battle start (T0) and adds effective Move Speed on every tick even while no approach intent exists. Movement itself is still gated by active, legal out-of-range approach intent; without it, the accumulated gauge cannot move the unit. With Move Speed 98, the gauge is 98 at T1 and 196 at T2; if a legal selected action requires approaching, one step occurs at T2 and 100 is spent, retaining 96 overflow. If Move Speed is 100 or more, a needed legal approach can step at T1. At most one space is moved per unit per tick; overflow remains banked. A same-tick Freeze affects that tick's effective speed as defined by action-before-movement resolution order.
10. `BattleEngine.simulateBattle`'s monster cast section contains one cast resolution per tick at most. In the supplied sample, one Ice Bolt damage event and the resulting Freeze application are both labeled T4; this is the expected pair of events from one successful status-proccing cast, not duplicate damage. The unexplained discrepancy is that the first Ice Bolt appears at T4 rather than T2. In the earlier test run, the initial Ice Bolt resolution at T2 passed, but the two-tick repeat cadence and high-speed movement assertions reflect the old behavior and must be replaced with the new T2/T6/T10 cooldown schedule and passive T0 movement-gauge accumulation (Move Speed 98: gauge 98 at T1, first eligible step T2). That run later failed at the Wailing Wraith Gambit-order assertion (root/frontend catalog mismatch). A precomputed battle log is immutable, so check whether the shown entry was generated by the older engine/catalog; do not infer a duplicate action from the paired status event.

## Mastery tree, tooltips, and independent drafts

- Mastery category XP, level, available points, spent points and skill ranks are independent for Sword, Greatsword, Dagger, Bow, Staff, Rod, Shield and Rune. XP earned with Bow never advances Rod Mastery.
- The category selector includes all eight categories. The selected category's tree is a vertical, extensible icon tree: current node 1 above node 2, connected by a visible prerequisite line. Each skill node itself is only a 64×64 icon, with `current/effective rank / max rank` below it; no rectangular text card.
- Create distinct original high-quality PNG icons for the 16 player skills and four current monster skills, inspired by `project/skill_icons.png` and illustrating each ability's actual function. Display at 64×64 in Mastery; the Grind monster skill row may render them smaller.
- Current skill tree identities/names after approval:
  - Rod node 1: **Light Wisp** (display-name change from Wisp Flow; preserve stable internal ID `wisp_flow` so learned ranks and saved Gambits remain valid); node 2 remains Light of Heaven.
  - Shield node 2: War Cry.
  - Rune node 1: **Arcane Dynamo** (new passive); node 2 remains Magic Barrier and its prerequisite changes to Arcane Dynamo rank 5.
  - Stored Essence definition/implementation remains deprecated/hidden legacy data and is not learnable in the new tree; the one-time reset clears its ranks along with every other allocated rank, without resetting Mastery XP or level.
- Clicking a skill icon stages exactly one rank locally if the selected category has an available point and the rank/prerequisite rules permit it. Pending rank/rank count appears green. There are no +/− buttons and no controls in tooltips. Reset discards only pending allocations in the **selected category**. Each category retains its own independent draft while switching categories. Apply commits only the selected category's valid pending draft atomically; no server mutation or queue change happens before Apply, and committed ranks can never be refunded by Reset.
- Apply uses one `BattleService.runFutureCombatMutation()` boundary. Preserve the in-flight battle snapshot/job; invalidate/rebuild only eligible future queue entries. Submit absolute target ranks (or an equivalent idempotent contract), validate the whole category draft under a row lock, and clear the draft only after successful response.
- Every authoritative `battle:resolved` event refreshes the authoritative rows for all categories. The client does not estimate XP, levels or points.
- Hover/focus tooltips are keyboard accessible, not clipped, contain no controls, and show skill name, active/passive kind, rank/max, prerequisite, SP cost, cast time, cooldown, base damage/heal/DEF formula, proc chance, stack/duration, and range/position effects as applicable. All numerical values are bold. Never estimate final damage against a target (DEF/MDEF and combat variance make that target-specific). Show deterministic skill base/formula values and rank deltas, e.g. `Base Damage 64 (+15)`; pending increments are green. After Apply, show the new authoritative value in normal color.
- **War Cry:** DEF bonus is `10 × active skill rank`, duration 15 ticks/seconds. Keep its existing catalogue SP cost and cooldown unless separately approved.
- **Light Wisp:** intended base damage is `MATK + 25 × active skill rank + floor(current SP before paying Light Wisp's own cost / 5)`. Sample SP before deducting this skill's own cost, and before any Arcane Dynamo refund from the resolved action. Current implementation does not include `25 × rank` and instead uses MATK + remaining SP after cost. Do not show target-specific final damage in the tooltip.

## Existing-rank reset and targeted cheat

- The change includes a one-time, transactional data reset over every existing character's `weapon_proficiencies` rows. Preserve each row's `characterId`, `weaponType`, `level`, and `xp`; replace `skillRanks` with an empty object and set `spentSkillPoints = 0`. Do not delete rows, reset XP, reset Mastery levels, or create extra points beyond the points already earned by the preserved level. The result is that every category's earned points are available for redistribution. This is a data-only migration/reset, not a schema change; it must run once as an explicit migration, not on every app startup.
- Add `POST /reset-skilltree/:characterName` as a targeted development/administrative cheat. Resolve an exact character name; reject missing or ambiguous matches. In one transaction lock the character and all its proficiency rows, clear the ranks and set each category's `spentSkillPoints` to zero, while preserving every category's XP and level. Return the authoritative resulting category rows and log the target/result. Protect the destructive route with the project's dev/admin guard and fail closed when the guard is unavailable; never expose it as an unrestricted production endpoint. This per-character reset is idempotent.

## Arcane Dynamo and legacy Rune skill

- Arcane Dynamo is a Rune-category passive and is active only when Rune equipment is present in the combat snapshot. After each successful basic attack or resolved active skill, refund SP equal to `2 × Arcane Dynamo rank` (rank 1–5 therefore returns 2/4/6/8/10 SP), capped at the character's max SP. A miss, an illegal/out-of-range action that does not resolve, cooldown/SP rejection, or periodic damage/status tick does not trigger the refund. Apply the refund once per successful action, not once per damage component, and record the amount in the event timeline.
- Stored Essence remains documented in source as legacy/deprecated, is not shown in the tree, and is unavailable for new allocation. The one-time reset clears all persisted skill ranks across every category for every existing character, so no Stored Essence ranks are migrated; Mastery category XP/levels remain unchanged and all points earned at those levels become available to redistribute.

## Monster mana and ability row

- Every current monster starts each encounter at full SP. Set `maxSp = 60` for all current monsters except `mon_venomviper` and `mon_wraith`, which use 80. Every monster regenerates 2 SP per 10 battle ticks, capped at max SP. The resource is deterministic and local to the current encounter; it does not persist as an independent character/monster database state across encounters.
- Monster skill costs: Enraged Strike (`monster_skill_massive_damage`) 30 SP; Regenerate (`monster_skill_self_heal`) 15 SP; Ice Bolt (`monster_skill_ice_bolt`) 10 SP; Ground Slam (`monster_skill_stun`) 30 SP. Existing Ice Bolt cost 0 is superseded.
- A monster skill resolves only if range/legal conditions, cooldown and current SP allow it. Cost is consumed exactly once on resolution; rejected/out-of-range/unselected skills do not consume SP or start cooldown. If no Gambit line is legal, the monster does nothing for that gauge fire, stays stationary, and has no implicit fallback action. Event snapshots record both character and monster SP.
- Grind shows the monster's blue SP bar immediately under HP. Below event logs and directly above `DROPS THIS SESSION`, show an icon-only row of distinct `use_skill` IDs referenced by the current monster's Gambit; hover/focus reveals canonical name, cost, cast time, cooldown and effect.

## Cooldown, Gambit idling, Disarm, and movement

- **Sequential cooldown contract:** cooldown begins on the tick an action resolves. `cooldownTicks = N` forbids another activation during the next N ticks; a new activation is eligible only after those blocked ticks. The gauge cannot start/advance a new cast while its action is cooling down. With Ice Bolt `baseCastTicks = 2`, `cooldownTicks = 1`: the initial Ice Bolt resolves at T2; T3 is blocked; T4 activates the next cast; T5 continues casting; T6 resolves it. T7 is blocked; T8 starts the next cast; T9 continues; T10 resolves. The test oracle for resolved Ice Bolt events is T2/T6/T10..., not T2/T5/T8 or T2/T4/T6. Cooldown does not overlap the cast time of the next action.
- The user's Wailing Wraith Gambit semantics remain: if Silenced, `attack`; otherwise `use_skill: monster_skill_ice_bolt`. Keep the canonical root `monsters.json` order (`silence → attack` first, Ice Bolt second), and sync this specific Wraith Gambit row/order to the frontend mirror without overwriting other catalogue differences. The evaluator filters actions by gauge and verifies each relevant line's conditions and legality, including SP, cooldown and range. An illegal Ice Bolt can be skipped according to normal Gambit evaluation; do not invent another fallback.
- If a gauge fires and no relevant Gambit line is legal, the combatant performs no action. There is no implicit attack, fallback, or movement intent. A legal out-of-range selected action may establish/maintain approach intent; Disarm makes the player character's basic Attack line illegal. If there is no other legal selected action needing approach, clear/prevent stale intent and do not approach solely to get in range. Preserve existing monster-specific Disarm movement behavior; this rule is for the player-controlled character only.
- **Movement gauge contract:** initialize the gauge at 0 at battle start/T0, then add effective Move Speed every battle tick regardless of whether `movementIntent` is currently true. The gauge is a charging meter, not a movement command. A unit moves only if an active legal selected action requires approaching an out-of-range target. When intent is active and the gauge is at least 100, move at most one space during that tick, subtract 100 and retain all remaining progress; if no legal intent exists, movement does not occur but the accrued gauge remains banked. With Move Speed 98, gauge is 98 at T1 and 196 at T2; if approaching is legally required, the unit moves at T2 and retains 96. With Move Speed >=100 and valid approach intent, the first possible movement is T1. Effective Move Speed penalties such as Freeze apply according to the current action/status-before-movement ordering; only movement (not gauge accumulation) is gated by intent.
- The sample trace's T4 Ice Bolt damage and T4 Freeze application are an expected damage-plus-proc pair from one cast, not duplicate damage. A first Ice Bolt event at T4 may reflect an older precomputed queue entry or backend process. Validate fresh queue generation/runtime against the tick-level sequence above; do not mutate existing immutable battle logs/entries retroactively.

## Finalized decisions — no open design questions

1. Light Wisp's `current SP / 5` bonus samples current SP **before paying Light Wisp's own cost**, before any Arcane Dynamo refund from that same action.
2. A one-time reset clears allocated ranks for every existing character and category, while preserving each category's XP and level; all spent points become available again. Consequently, old Stored Essence ranks are not migrated. The targeted cheat resets one named character with the same preservation rules.
3. Cooldown is sequential as specified above. For Ice Bolt, a cast resolved at T2 blocks activation on T3; the next cast starts at T4 and resolves at T6.
4. The Disarm/no-approach rule applies to the player-controlled character only. Preserve the current monster-specific behavior.
5. The final standalone “4.” in the earlier message did not introduce any additional requirement beyond the explicit numbered decisions; the current proposal includes all listed requested changes.
